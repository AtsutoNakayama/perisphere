## 確認 1: SSR（Next.js 等）対応のメリット / デメリット比較（元 Q8）

### A) SSR 対応を要件に含める場合

**メリット**:

- Next.js は React の主要フレームワークであり、汎用 OSS として公開する方針（Q13 = A）では SSR セーフであることが事実上の前提になる。非対応だと import しただけで `window is not defined` で落ち、利用者に `next/dynamic`（`ssr: false`）等の回避策を強いる
- 対応コストは小さい: 「モジュール読み込み時にブラウザ API（window / document / WebGL）へ触れず、マウント後に初期化する」という設計規律が中心で、大きな追加実装は不要
- コアを DOM 非依存に保つ規律は、将来の Vue 対応（Nuxt も SSR が主流）やユニットテストの容易性にもそのまま効く

**デメリット / 限界**:

- SSR 環境（Next.js）が動作確認マトリクスに加わる
- WebGL キャンバスの中身はサーバーでは描画できないため、SSR で得られるのは「エラーなく動き、プレースホルダ HTML を返せる」まで（SEO 目的の完全な事前描画は原理的に不可能）
- ハイドレーション前後のちらつき対策など、設計上の考慮点が少し増える

### B) SPA のみの場合

**メリット**: 検証範囲が最小になり、初期開発が最速

**デメリット**: Next.js（特に App Router はサーバー実行がデフォルト）利用者の導入体験が悪化し、OSS としての採用障壁・Issue 発生源になる。後から SSR セーフ化するにはモジュール構造の見直しが必要になり、後付けの方が高くつきやすい

**推奨**: A（SSR 対応を要件に含める）— コストが小さい割に採用面の効果が大きく、汎用 OSS 方針・将来の Vue / Nuxt 展開と整合するため。

### Clarification Question 1

A) SSR 対応を要件に含める（推奨）

B) SPA のみを想定する（SSR 対応は将来検討）

X) その他（下の [Answer]: タグの後に記述してください）

[Answer]:A

## 確認 2: three.js の依存形態 — A（peerDependencies）が望ましい理由（元 Q12）

「B（dependencies 内包）が一般的」というご認識は、**ユーティリティ系の依存**（内部実装の詳細として使う小さなライブラリ）については正しいです。一方、**three.js のような「大型・シングルトン的・利用側アプリも直接触り得るフレームワーク級」の依存は peerDependencies にするのが npm エコシステムの慣行**です（react や vue 自体を peer にするのと同じ理由）。実際、three.js エコシステムの代表的な React 向け統合ライブラリ群は、いずれも three を peerDependencies にしています。

### A（peerDependencies）が望ましい具体的な理由

1. **二重バンドルの防止**: three.js は minify 後 600KB 級の大型依存。利用アプリが three.js を直接使う場合（独自の 3D 表現、本ライブラリのカスタム拡張）、内包すると three が 2 つバンドルされサイズがほぼ倍増する
2. **「2 つの three」による実行時バグの防止**: three はクラスの `instanceof` 判定や WebGL 状態管理を前提としており、別インスタンス / 別バージョンの three が混在すると `instanceof THREE.Texture` の失敗など、デバッグ困難な不具合を生む（React が二重に入ると壊れるのと同型の問題）
3. **バージョンの主導権が利用者に残る**: three.js は毎月リリースされ変化が速い。peer + サポート範囲の明記なら、利用者がセキュリティ修正や新機能を自分のタイミングで取り込める。内包だと本ライブラリの更新を待たないと three を動かせない
4. **拡張 API との整合**: 本ライブラリは「カスタムビューワーモードの追加」などの拡張 API を要件とするため、three のオブジェクト（カメラ・シーン等）を公開 API で受け渡す場面が想定される。その場合、利用側と同一の three インスタンスを共有することが事実上必須であり、peer が自然

### B（dependencies 内包）のメリット（参考）

1. インストールが 1 パッケージで完結する
2. ライブラリが検証済みの three バージョンを固定でき、互換性問題の報告が減る

**補足**: npm v7 以降は peerDependencies を自動インストールするため、A でも導入体験は実質 `npm install @perisphere/react` の 1 コマンドで済みます（three は自動で入る）。サポートする three のバージョン範囲を package.json とドキュメントに明記し、CI で範囲の両端を検証すれば、B のメリット 2 も概ねカバーできます。

**推奨**: A（peerDependencies）。

### Clarification Question 2

three.js への依存はどう扱いますか？

A) peerDependencies にする（推奨 — three.js エコシステムの慣行。npm v7+ では自動インストールされるため導入体験はほぼ変わらない）

B) dependencies として内包する

X) その他（下の [Answer]: タグの後に記述してください）

[Answer]:A

## 確認 3: RTO/RPO 目標と災害復旧（DR）戦略【Resiliency Baseline 必須確認】

オプトインいただいた Resiliency Baseline（RESILIENCY-02）が Requirements 確定前に必須としている確認です。

**本プロジェクトの文脈**: 成果物は「npm パッケージ（レジストリ配布）」と「ドキュメント / デモサイト（静的ホスティング想定）」で、自前で稼働させるサーバーや永続データストアを持たない見込みです。その場合、可用性・復旧は npm レジストリと静的ホスティング基盤（GitHub Pages 等）に委譲され、ソースは Git で完全に復元可能なため、**E が実態に最も近い選択肢**です。

### Clarification Question 3

RTO（目標復旧時間）/ RPO（目標復旧時点）の目標はどれですか？ これにより DR 戦略とインフラの冗長化レベルが決まります。

A) RPO/RTO: 数時間 — Backup & Restore 戦略。最低コスト（$）。データはバックアップのみ、サービスは未デプロイ。障害時に IaC から再デプロイしバックアップから復元。非クリティカルなワークロード向け

B) RPO/RTO: 数十分 — Pilot Light 戦略。コスト $$。データは稼働、サービスはアイドル状態で配置し、フェイルオーバー時にスケールアップ。重要なワークロード向け

C) RPO/RTO: 数分 — Warm Standby 戦略。コスト $$$。データは稼働、サービスは縮退稼働させ、フェイルオーバー時にスケールアップ。ビジネスクリティカルなアプリケーション向け

D) RPO/RTO: ほぼリアルタイム — Multi-site Active/Active 戦略。最高コスト（$$$$）。複数リージョンで同時稼働。ミッションクリティカル・ゼロダウンタイム要件向け

E) N/A — シングルリージョンで許容（クロスリージョン DR 不要）。本プロジェクトでは可用性を npm レジストリ / 静的ホスティング基盤に委譲する

X) その他（下の [Answer]: タグの後に記述してください）

[Answer]:E
