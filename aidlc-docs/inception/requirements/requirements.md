## 2. 背景と目的

360°写真（全天球パノラマ）の Web 表示では、視点操作の滑らかさに加えて、投影方法（ビューワーモード）の切り替えが表現の幅を決める。クリスタルボールや小惑星のような多彩な見せ方を Web ページ上でそのまま提供できることに、本ライブラリの価値がある。

perisphere は **「投影モードの豊富さ」と「拡張性」を中核価値**とする 360°写真ビューワーライブラリであり、以下を目的とする。

1. 多彩なビューワーモード（7 種の投影プリセット）を Web ブラウザで提供する
2. React アプリケーションへ容易に組み込める API を提供する
3. フレームワーク非依存のコアにより、将来の Vue 等への展開とコミュニティによる機能拡張を可能にする
4. 汎用 OSS として公開し、広い採用を目指す

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| エクイレクタングラー | 正距円筒図法で全天球を 2:1 の矩形に展開した画像形式。360°写真の事実上の標準 |
| ビューワーモード | 球面画像を 2D 画面に映す投影方法のプリセット |
| 標準ビュー | 球の中心から内側を見る一般的な透視投影（既定モード） |
| 超広角（UltraWide） | 広い視野角で広範囲を一望する投影。周辺の歪みは許容 |
| デワープ（Dewarp） | 広めの視野角を保ちつつ歪みを軽減した投影 |
| リニア（Linear） | 直線が直線のまま映る歪みゼロの直線投影（視野角は狭め） |
| パニーニ（Panini） | 円筒系とステレオ系を合成した投影。広い視野角と低い歪み（特に垂直線の直線性）を両立する、パノラマ分野で確立された投影手法 |
| 小惑星（Tiny Planet） | ステレオグラフィック投影で球全体を「小さな惑星」状に見せる表現 |
| クリスタルボール | 球の外側から球面を眺め、ガラス玉のように見せる表現 |
| ヘッドレス利用 | 同梱 UI を使わず、API のみでライブラリを操作する利用形態 |

注: 各モードは確立された投影手法（透視投影・ステレオグラフィック投影・パニーニ投影等）の組み合わせとパラメータ設定で実現する。合成投影の具体的なパラメータは設計ステージで確定する。

## 4. 機能要件

### A. 画像入力

#### FR-01: エクイレクタングラー画像の表示

エクイレクタングラー形式（アスペクト比 2:1）の JPEG / PNG 画像を読み込み、全天球パノラマとして表示できること。画像サイズに固定の上限値は設けない（API として寸法上限で読み込みを拒否しない）。実際に表示可能な最大サイズは実行環境の WebGL 最大テクスチャサイズに依存し、それを超える画像は安全に縮退する（FR-18・SECURITY-11）。

- 受け入れ基準: 8K（7680×3840）のエクイレクタングラー JPEG/PNG を**動作保証**範囲として表示できる（性能目標は NFR-01）
- 受け入れ基準: 8K を超える画像も上限エラーで一律拒否せず読み込みを試みる。環境上限を超える場合はエラーイベント通知と安全なフォールバックに倒す（FR-18）
- 受け入れ基準: URL 指定で画像を読み込める（CORS 対応画像）

#### FR-02: 入力フォーマットの拡張機構

入力フォーマットを後付けで追加できるアダプタ構造を持つこと。初期実装はエクイレクタングラーのみだが、将来キューブマップ・デュアルフィッシュアイ・360°動画等のソースを、コアの改修なしに追加実装できるインターフェースを定義する。

- 受け入れ基準: 画像ソースの解釈（テクスチャ生成）が交換可能な抽象として分離されている

### B. ビューワーモード

#### FR-03: 7 種のビューワーモード

以下の 7 種のビューワーモードを提供すること。

1. 標準ビュー（既定）
2. 超広角（UltraWide）
3. デワープ（Dewarp）
4. リニア（Linear）
5. パニーニ（Panini）
6. 小惑星（Tiny Planet）
7. クリスタルボール（Crystal Ball）

- 受け入れ基準: 各モードを API および同梱 UI から選択でき、表示が当該投影の見た目特性を満たす
- 受け入れ基準: 各モードで視点操作（FR-06〜FR-08）が破綻なく機能する

#### FR-04: モード切替 API

ビューワーモードを実行時に切り替えられること。初期リリースは即時切替とするが、将来スムーズなアニメーション遷移を追加できる API 形状（切替オプション引数等）とすること。

- 受け入れ基準: モード切替 API 呼び出しで表示が即時に切り替わり、切替イベントが発火する

#### FR-05: カスタムビューワーモードの追加機構

利用者が独自の投影（カスタムビューワーモード）を定義してビューワーに登録できる拡張 API を提供すること。同梱 7 モード自体もこの機構の上に実装し、拡張機構の実用性を担保する。

- 受け入れ基準: 同梱モードと同じインターフェースでカスタムモードを登録・選択できる

### C. 視点操作

#### FR-06: ポインタ操作

マウスドラッグによる視点移動（パン / チルト）と、マウスホイールによる拡大縮小（ズーム）ができること。

- 受け入れ基準: ドラッグで視点が連続的に追従し、ホイールで FOV/ズームが滑らかに変化する

#### FR-07: タッチ操作

モバイルブラウザにおいて、1 本指ドラッグによる視点移動と、ピンチによる拡大縮小ができること。

#### FR-08: キーボード操作と写真の選択移動

キーボードで主要操作（写真の前後切替・視点移動・ズーム・フルスクリーン切替・モード切替）が完結できること。矢印キー（または設定されたキー）で前後の写真へ移動できること。キーマップは利用側で変更・無効化できること。

- 受け入れ基準: 既定キーマップで写真切替・視点操作・ズームがキーボードのみで行える
- 受け入れ基準: キーボード操作の有効/無効とキー割り当てを設定できる

#### FR-09: ズーム範囲の制御

拡大縮小（FOV 変化）の上限・下限を設定でき、既定値はモードごとに適切な範囲を持つこと。

### D. フルスクリーン

#### FR-10: フルスクリーンモード

ビューワーをフルスクリーン表示に切り替え・解除できること（API・同梱 UI ボタン・キーボードの 3 経路）。状態変化はイベントで通知すること。

- 受け入れ基準: Fullscreen API が使える環境でフルスクリーン切替が動作し、非対応環境（iOS Safari 等）では代替動作（擬似フルスクリーン等、設計で確定）にフォールバックする

### E. ギャラリー（複数写真）

#### FR-11: ギャラリー API

複数写真のリストを読み込み、前後切替・インデックス指定表示ができる API を提供すること。切替時はイベントを発火すること。

- 受け入れ基準: 写真リストの設定、`next()` / `prev()` / インデックス指定の各操作、切替イベントの購読ができる

#### FR-12: 標準ギャラリー UI

サムネイル一覧またはページインジケーター等の標準ギャラリー UI を同梱すること。非表示化・スタイルカスタマイズが可能であること。

#### FR-13: バーチャルツアー拡張点

写真内ホットスポットから別写真へ遷移する「バーチャルツアー」機能を、将来コア改修なしに追加できる構造（シーングラフへのオーバーレイ配置と相互作用の拡張点）を持つこと。初期リリースでの実装はスコープ外。

### F. UI 提供形態

#### FR-14: 標準コントロール UI の同梱

フルスクリーン・ズーム・ビューワーモード切替・写真切替等の標準コントロール UI を同梱すること。コントロールは個別に表示/非表示を設定でき、スタイルをカスタマイズでき、全体を無効化したヘッドレス利用も選択できること。

#### FR-15: UI 文言の差し替え

同梱 UI の表示文言・aria-label を利用側で差し替えられること（i18n は利用側の責務とし、ライブラリは差し替え手段を提供する）。

### G. API・イベント・React 対応

#### FR-16: React アダプタ

React コンポーネントおよびフックとしてビューワーを利用できること。命令的操作（モード切替・写真切替等）のためのハンドル（ref）を提供すること。

- 受け入れ基準: React コンポーネントの宣言的 props と、ref 経由の命令的 API の双方で主要機能を操作できる

#### FR-17: イベント API

少なくとも以下のイベントを購読できること: 初期化完了、読み込み進行、読み込みエラー、視点変更、ズーム変更、モード切替、写真切替、フルスクリーン変化。

#### FR-18: エラー処理とフォールバック表示

画像読み込み失敗・WebGL 非対応・WebGL コンテキストロストを検出し、エラーイベント通知と安全なフォールバック表示（エラー状態の明示）を行うこと。内部実装の詳細（スタックトレース等）をエンドユーザー向け表示に出さないこと。

## 5. 非機能要件

#### NFR-01: 性能

**動作保証（性能目標）の上限を 8K**（7680×3840）とし、8K までのエクイレクタングラー画像を一括ロードで表示したとき、主要対象環境において視点操作・ズームが滑らか（60fps 目安）であること。8K を超える画像の読み込みは API として拒否しない（FR-01）が、滑らかさ・メモリ・成否は環境依存とし性能保証の対象外とする。プログレッシブ/マルチ解像度ローディングは初期スコープ外（将来拡張）。

#### NFR-02: 対象環境

デスクトップ（Chrome / Edge / Firefox / Safari 最新世代）およびモバイル（iOS Safari / Android Chrome）。WebGL 2 を前提とする。ジャイロ操作は初期スコープ外だが、入力ハンドリングを拡張可能な構造とする（FR-02/FR-05 と同様の拡張点）。

#### NFR-03: SSR セーフ

Next.js 等の SSR 環境で、モジュール import 時にブラウザ API（window / document / WebGL)へアクセスせず、エラーなくレンダリングできること。ビューワー本体はクライアントマウント後に初期化されること。

#### NFR-04: アクセシビリティ

キーボードのみで主要操作が完結すること（FR-08)。フォーカス管理と ARIA 属性を適切に付与し、UI 文言は差し替え可能であること（FR-15）。

#### NFR-05: アーキテクチャ（保守性・拡張性）

フレームワーク非依存のコア（`@perisphere/core`）と React アダプタ（`@perisphere/react`）を分離したモノレポ構成とし、将来 `@perisphere/vue` 等のアダプタをコア改修なしに追加できること。拡張点（入力フォーマット・ビューワーモード・入力デバイス・将来のツアー/動画）を明確な公開インターフェースとして設計すること。

#### NFR-06: 依存方針

three.js は **peerDependencies** とし、サポートするバージョン範囲を package.json とドキュメントに明記すること。その他のランタイム依存は最小限に保つこと。

#### NFR-07: 配布形態

npm 公開（モノレポからの分割パッケージ）。ESM 配布 + TypeScript 型定義を提供し、tree-shaking 可能であること。CDN/UMD ビルドは初期スコープ外。

#### NFR-08: ドキュメント・デモ

汎用 OSS としての採用を目指し、API リファレンス・デモサイト（全ビューワーモードを体験可能）・利用サンプル（React / Next.js）を整備すること。

#### NFR-09: テスト戦略

ユニットテストに加えプロパティベーステスト（PBT）を全面適用する（拡張オプトイン: Yes）。投影計算・座標変換・状態管理（ギャラリー・モード切替）が PBT の主対象候補。PBT フレームワーク選定（TypeScript では fast-check が有力）は Construction の NFR Requirements ステージで確定する。ビジネスクリティカルなパスは example-based テストを併設する（PBT-10）。

#### NFR-10: セキュリティ（Security Baseline 適用、ライブラリ文脈）

- 公開 API の入力検証: 型・範囲・形式の検証を行い、不正入力は明確なエラーとする（SECURITY-05）
- 例外の安全処理: 外部リソース読み込み等の失敗を捕捉し、フェイルセーフに倒す。リソース（WebGL コンテキスト・イベントリスナー・テクスチャ）を確実に解放する破棄 API を持つ（SECURITY-15）
- エラー表示に内部詳細（スタックトレース・内部パス）を含めない（SECURITY-09）
- サプライチェーン: lockfile のコミット、依存脆弱性スキャンの CI 組み込み、CI アクション/ツールのバージョン固定、公式レジストリのみ利用（SECURITY-10、SECURITY-13）
- セキュア設計: 誤用ケース（不正画像 URL、巨大画像、悪意ある寸法）を設計で考慮する（SECURITY-11)

#### NFR-11: レジリエンシー（Resiliency Baseline 適用、ライブラリ文脈）

- RTO/RPO・DR 戦略: **N/A（確認 3 = E）**。稼働サーバー・永続データストアを持たず、可用性は npm レジストリおよび静的ホスティング基盤（デモサイト）に委譲する。ソース・成果物は Git と npm レジストリから復元可能
- 変更管理プロセス: **既存の GitHub Flow 運用を採用（確認 4 = A）** — Issue 起点、main ブランチ保護、PR 必須、CI 必須チェック、レビュー承認、Squash merge（`CONTRIBUTING.md`）。**正式版リリース時はリリースブランチを作成する**（運用詳細は Construction フェーズのリリース設計で確定）
- 障害分離（ライブラリ文脈への適用、RESILIENCY-10 準拠）: 画像読み込みの失敗・タイムアウトを安全に処理し、ビューワー全体を巻き込まず縮退する（FR-18）。WebGL コンテキストロストからの復帰を試みる

#### NFR-12: ライセンス・OSS 運用

MIT License（リポジトリ既存の `LICENSE`）。Conventional Commits・`CONTRIBUTING.md` のブランチ運用に従う。

## 7. 前提・制約

- レンダリング基盤は three.js（初回要望による技術要件）。three.js は WebGL 2 を前提とする近年版を採用（バージョン確定は NFR Requirements ステージ）
- 開発言語は TypeScript を前提（型定義配布 NFR-07 の帰結。最終確定は NFR Requirements ステージ）
- パッケージ名は perisphere 系（`@perisphere/*`）を想定（npm スコープの可用性確認は Construction で実施）
- 製品コードの実装は本 Issue（#21）のスコープ外であり、Inception 完了後に unit 単位の後続 Issue で実施する
- 命名・言及ポリシー: 公開 API・UI・ドキュメントで用いる機能名・モード名は、一般的な投影用語または本プロジェクト独自の中立な名称のみとし、第三者の商標・製品名・ブランド名を使用しない。公開文書では他社製品や既存の類似ライブラリに言及しない（総称としての言及・比較を含む）。動機・価値は比較によらず肯定形で記述する

## 8. リスク

| リスク | 影響 | 対応方針 |
|---|---|---|
| 合成投影（パニーニ等）の見栄え調整が主観評価に依存する | 目標品質の判定が曖昧になり手戻りが生じる | 投影パラメータを調整可能な設計とし、実画像での比較検証を設計・テストに組み込む |
| 投影数学の実装誤り | 表示の歪み・破綻 | 投影計算を純粋関数として分離し PBT（ラウンドトリップ・不変条件）を適用（NFR-09） |
| モバイル実機での性能・メモリ制約（8K テクスチャ） | 低速端末でのクラッシュ・カクつき | 端末能力に応じたテクスチャ上限・ダウンサンプリングを設計で考慮 |
| three.js の高速な API 変化（peer 依存） | 利用者環境での互換性問題 | サポート範囲の明記と CI での範囲検証（NFR-06） |
